# 仕組み

capability-router の目的は次のとおりです。

- LLM エージェントや利用者が、自分の基準でタスクを任せるモデルと推論の強さの組（config）を選べます。
- 委任する作業を、残量に応じて複数の定額 AI サブスクリプションに振り分けられます。

目的を実現する工夫は次の 4 つです。

<a id="items"></a>
## 1. 物差しは利用者が作る

**制約**：プロンプトルーターや公開リーダーボードでは、他人の学習データやベンチマークをもとに「能力がある」と判断します。

**工夫**：利用者が能力項目を定義し、各項目の 4 段（`none`/`low`/`mid`/`high`）をアンカー問題で定めます。タスクの要求と config の能力を同じ段で表し、`route` で比べます。

**限界**：実際に使う定義とカタログは同梱していません。割り当ての質は、利用者が測った能力の値に左右されます。

<a id="caller-estimates"></a>
## 2. 呼び出し側の LLM が要求を見積もる

**制約**：ルーターが読めるのはタスクの文面だけです。委任するエージェントが見ている会話やリポジトリは読めません。

**工夫**：`capability-router criteria` は、定義をもとに各段のアンカー問題を並べた基準を作ります。委任するエージェントは基準を読み、同梱の[スキル](../skills/capability-router/SKILL.md)に従って全項目の段を `--levels` に渡します。

**限界**：エージェントがいなくても、外部 API の Jev で要求を見積もれます。ただし、Jev が読めるのはタスクの文面だけなので、お勧めしません。

<a id="service-first"></a>
## 3. サブスクリプションの余りでサービスを先に選ぶ

**制約**：週や月ごとに上限がある定額サブスクリプションを価格だけで選ぶと、1 つの枠を使い切ってしまいます。他のサービスでは枠が余ったままリセットを迎えます。

**工夫**：基準ペースで使った場合より多く残っている分が「余り」です。`route` は余りの大きいサービスを先に選び、その中で config を決めます。

**限界**：サービスを先に選ぶため、軽いタスクに大きな config が選ばれることがあります。

<a id="ids-only"></a>
## 4. モデルを呼ばず、選ぶだけにする

**制約**：モデルの呼び出しを仲介するプロキシは、サービスごとの起動方法すべてに対応する必要があります。CLI、フラグ、推論の強さの名前などは、サービスによって異なります。

**工夫**：`route` が返すのは、`example-mid cursor` のような `<config> <service>` の 1 行だけです。呼び出し側が、カタログファイルの `model` と `effort` を使って選ばれたサービスを起動します。

**限界**：config ID と起動時のオプションの対応は、利用者が書きます。
