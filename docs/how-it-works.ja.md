# 仕組み

capability-router の目的は次のとおりです。

- LLM エージェントや利用者が、自分の基準でタスクを任せるモデルと推論の強さの組（config）を選べます。
- 委任する作業を、残量に応じて複数の定額 AI サブスクリプションに振り分けられます。

目的を実現する工夫は次の 4 つです。

<a id="items"></a>
## 1. 物差しを利用者が作る

**制約**：プロンプトルーターや公開リーダーボードでは、他人の学習データやベンチマークをもとに「能力がある」と判断します。

**工夫**：利用者が能力項目を定義し、各項目の 4 段（`none`/`low`/`mid`/`high`）をアンカー問題で定めます。タスクの要求と config の能力を同じ段で書いて `route` で比べます。

**限界**：定義とカタログの実物は同梱しないので、割り当ての質は利用者の測定で決まります。

<a id="caller-estimates"></a>
## 2. 呼び出し側の LLM が要求を見積もる

**制約**：ルーターはタスクの文面しか参照しないため、委任するエージェントが参照している会話やリポジトリは参照できません。

**工夫**：`capability-router criteria` で定義から各段のアンカー問題を並べた基準を作ります。委任するエージェントは基準を読み、同梱の [スキル](../skills/capability-router/SKILL.md) の手順で全項目の段を `--levels` に渡します。

**限界**：エージェントなしでも外部 API の Jev で見積もれますが、文面しか参照しないため勧めません。

<a id="service-first"></a>
## 3. サブスクリプションの余りでサービスを先に選ぶ

**制約**：週や月に上限がある定額サブスクリプションを価格だけで選ぶと、1 つを使い切り、他は余ったままリセットを迎えます。

**工夫**：`route` ではまず、基準ペースより多く残っている（余りが大きい）サービスを選びます。続いて、選んだサービスの config から選びます。

**限界**：サービスを先に選ぶため、軽いタスクに大きな config が選ばれることがあります。

<a id="ids-only"></a>
## 4. モデルを呼ばず、選ぶだけにする

**制約**：モデルの呼び出しを仲介するプロキシでは、サービスごとに異なる起動方法（CLI、フラグ、推論の強さの名前）すべてに対応する必要があります。

**工夫**：`route` は `example-mid cursor` のような `<config> <service>` の 1 行を返すだけです。呼び出し側で、カタログファイルの `model` と `effort` を使って選ばれたサービスを起動します。

**限界**：config ID と起動側のオプションの対応は、利用者が書きます。
