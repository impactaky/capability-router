# capability-router の設計判断

[English](design.md)

現在も有効な決定と理由を記します。動作と形式は[仕様](spec.ja.md)を参照してください。

## 何を実現しますか

タスクの要求と config の能力を同じ項目で表し、突き合わせます。routing のコードは model 名も項目名もカタログの値も知りません。model 固有の情報は利用者のカタログに、項目の定義は利用者の `capabilities.yaml` に置きます。repo はどちらも同梱しません。

## どの形と対象にしますか

| 決定 | 理由 |
|---|---|
| CLI と skill にします。`<config id> <サービス id>` を 1 行で返し、model は呼びません。 | 呼び出し側が model を起動します。複数サービスで動く config もあり、shell の `read` で 2 列を分けられます。 |
| routing の単位は model と reasoning effort の組である config です。 | reasoning effort で能力・cost・latency が変わるため、別々に route します。 |
| 文章の仕上がりが主目的なら、呼び出し側が文章向け config を直接指定します。 | 文章の質を項目で扱うかは利用者の判断です。呼び出し側が直接選べます。 |
| 項目もカタログの値も評価データも同梱しません。 | 利用者自身の能力の捉え方があって初めて役立ちます。同梱すると特定の外部 source の語彙に縛られます。 |

## 項目をどう定めますか

| 決定 | 理由 |
|---|---|
| 全項目を利用者が `capabilities.yaml` に定義します。`measures`、`excludes`、段の文章、アンカー、閾値です。 | 必要な能力は利用者とタスクで違います。router は汎用のままにします。 |
| 段はその段のアンカー問題 (`examples`) で定義します。段の文章はその要約とし、アンカーの無い段は文章だけで判断し、閾値は仮置きとします。 | 文章だけでは読み方が割れますが、アンカー問題があれば段の意味が定まります。仮置きであることも明示できます。 |
| カタログの項目は `score` (0..1) か `level` (`H`/`M`/`L`/`-`) のどちらかです。 | score を測った利用者は score を、アンカーを回した利用者は level を書けます。どちらも同じ尺度に乗ります。 |
| 全項目に `cost_per_task` と `time_per_task_s` を必須にし、単位を持たせません。 | cost と時間は項目と config で違いますが、単位は利用者ごとに違います。全 config で同じ値にすれば、無効化せず比較を実質無効にできます。 |
| 実値のカタログやテンプレートを同梱しません。`examples/` は架空と明記し、形だけを示します。 | 同梱値は推奨として読まれ、古くなります。 |

## 要求を誰が見積もりますか

| 決定 | 理由 |
|---|---|
| 基本は呼び出し側の LLM が見積もり、`--levels` で渡します。Jev は省略時の CLI 機能として残します。 | 呼び出し側は会話や repo も知っています。skill は推定経路を一つにします。 |
| LLM 向けの基準は `capability-router criteria` で定義から生成し、LLM はその file を読みます。Jev は定義の `question` と `levels` を読みます。 | 正本を一つにします。生成 file は定義の hash を持ち、古い copy に気付けます。 |
| 足りる最も低い段を成果物で選び、タスクの指示を読むこと自体は要求に数えません。 | 曖昧な程度の言い方は `mid` に偏り、指示の遵守まで数えると要求が膨らみます。 |
| 見積もりが終わるまでカタログの score を見ません。 | 通したい model から要求を逆算しないためです。 |
| Jev には項目ごとの Score 質問を 4 段で渡し、最多確率の段を採ります。model 選択は聞きません。 | Jev は小さな問いに向きます。要求と能力を分けます。 |
| Jev の Noul は使いません。 | 画像と入力長は metadata、tool use は全 config、latency は mode で扱えます。 |

## score と閾値をどう定めますか

| 決定 | 理由 |
|---|---|
| score は絶対値に保ちます。カタログの `score` はその値、`level` はその項目の閾値（閾値が無ければ固定の中間点）に対応させます。 | カタログや pool が変わっても config の値は動きません。絶対値なら利用者の閾値が意味を持ち続けます。 |
| 閾値は利用者の定義から読み、router は pool から導出しません。 | 合格点は利用者が決めます。pool 相対の階段は利用者の下で動き、選択を隠します。`examples/thresholds.py` は offline の補助 script です。アンカーの無い項目に仮置きの閾値を提案し、利用者が定義に貼ります。router は実行も導出もしません。 |
| どこかの config が score で書く項目には `thresholds` を必須にし、無ければ読み込み時に失敗します。 | 合否の基準が無い score は判断に使えません。黙って推測するよりエラーが適切です。 |
| 順位には要求 level を重みにした加重幾何平均を使います。 | 加重和は弱い項目を隠し、最小値は極端です。 |

## config をどう選びますか

| 決定 | 理由 |
|---|---|
| 基本は要求を満たす最安 config です。`balanced` は score が十分上がるときだけ乗り換えます。 | 足切り後の能力差は余裕なので、小さな差に費用を払いません。 |
| cost は要求項目の `cost_per_task` の合計です。何も要求しなければ全項目の合計です。 | 全項目の合計では、実際には走らない項目の費用も含まれます。 |
| 要求項目に値が無い config は `cheap` / `balanced` の比較から外し、時間が無ければ `fast-balanced` の乗り換え先から外します。 | 部分和や推定値で比べません。 |
| `time_per_task_s` を選択に使うのは `fast-balanced` だけです。`time_cost_band` と `time_ratio` を満たす最速へ乗り換えます。 | 速さが必要かは呼び出し側が判断します。無制限の最速選択は費用を増やします。 |
| 誰も通らなければ、最も多くの config を落とす項目から 1 段ずつ緩めます。 | 要求の形を残し、緩めた内容も確認できます。 |

## pool と data をどう管理しますか

| 決定 | 理由 |
|---|---|
| 能力の値はカタログ、有効・無効と所属サービスは `pool.yaml` に分けます。全 config をキーにして `services` と `enabled` を書きます。置き場は[setup](setup.ja.md)を参照してください。 | 値と運用上の所属は更新理由が違います。書き忘れによる無効化も防ぎます。値は利用者の XDG 領域に置きます。 |
| カタログは項目単位にします。1 config 1 file で、項目ごとに `score` か `level`、cost、time を書きます。 | routing のコードと利用者の項目名を切り離し、1 項目の価格付けが無関係な値を巻き込みません。 |
| `sanity.yaml` は固定 level の割り振りを表示し、期待値とは照合しません。ケースは本文を持ちません。 | router は level だけを受け取ります。期待表は pool の変更に追従しにくいためです。 |
| 委任を記録し、呼び出し側が `log outcome` を追記します。routing は log を読みません。 | 後から速さと合否を確認できます。 |

## 使用量をどう取得しますか

| 決定 | 理由 |
|---|---|
| `usage` は全サービスの残量と状態を JSON でも返します。 | 利用者と `route` が同じ状態を確認できます。 |
| 取得先と `SERVICE_IDS` は `usage.py` に置きます。`availability.py` と `scoring.py` は snapshot の値と ID だけを読みます。 | routing のコードを model と取得先に依存させません。 |
| 4 サービスを並行に取得し、各サービスを 30 秒で打ち切ります。失敗は `status` に入れ、終了コードは 0 です。 | 一つの遅延や失敗が他を止めません。 |
| `unavailable` と `error` を分けます。 | 前提が無い場合と取得失敗を区別できます。 |
| Codex と Claude Code は codexbar の OAuth source を指定します。 | 保存済み認証を使えます。既定の `auto` は遅くなります。 |
| Cursor Pro は cursor-agent の `auth.json` の `accessToken` で `GetCurrentPeriodUsage` を呼びます。残り%は `remaining` / `limit` から求め、`refreshToken` と `totalPercentUsed` は使いません。 | refresh は既存 session を無効にする恐れがあり、`totalPercentUsed` の単位は不明です。 |
| Command Code は `COMMAND_CODE_API_KEY` と CLI と同じ `/alpha` API を使います。月枠には CLI のプラン表を使い、作れなければ残高だけを出します。 | API は月付与額を返しません。転記元の `dist/cli.mjs` と `getPlanTotalCredits` は `usage.py` のコメントにあります。 |
| 個人の path と API key は環境変数で渡します。message はサニタイズし、外部コマンドの stderr は捨てます。 | 秘密値やアカウント情報を repo と出力に残しません。 |

## 使用量でどう選びますか

| 決定 | 理由 |
|---|---|
| まずサービスの段と余りで選び、その中で mode を適用します。 | 定額契約では余っている枠が重要です。 |
| 余りは経過時間から求めた期待使用率と実使用率の差です。週・月枠の最小値を使います。 | 同じ残量でも補充までの時間で意味が変わります。全サービスで同じ式を使います。 |
| 短期枠は余りに入れず、`low_5h_percent` 以下なら `low_5h` として後回しにします。どの枠でも残りゼロなら選びません。 | 短期枠はすぐ戻りますが、尽きそうなサービスは確実に後ろへ送ります。 |
| `offset` は利用者の services 設定に置きます。 | 契約や用途ごとの優先度は利用者によって違います。 |
| リセットチケットは数えません。`ticket: true` の週枠は残り%を余りにし、ゼロなら選びません。 | チケットを使った結果は次の取得に現れます。 |
| `scoped` な枠は読みません。 | 対象 config が分からないままサービス全体を止めないためです。 |
| 使用量を取れなければ余り 0 + `offset` の `normal` とします。 | 取得失敗だけで選択不能にしません。理由は `--explain` に出します。 |
| `route` は使用量を 5 分キャッシュします。`sanity` は使用量と services 設定を読みません。 | 毎回の取得を避け、`sanity` の結果を個人設定や時刻から独立させます。 |
| 使用量で全 config が落ちても要求は緩めません。 | 緩めても選べるサービスは増えません。 |

## どの案を採りませんでしたか

- **prompt から model 名を直接分類する案:** model の入れ替えごとに分類器が必要です。
- **既定の能力定義を同梱する案:** ある利用者の項目が全員の項目になり、能力の捉え方が一つに固定されます。
- **閾値を実行時に pool から導出する案:** 利用者の合格点がカタログに追従して動き、選択が隠れます。offline の補助 script はアンカーの無い項目の出発点を提案するだけで、利用者が定義に採否を決めます。
- **順位や件数で閾値を切る案:** level の意味が失われます。
- **加重和:** 弱い項目を隠します。
- **Jev に model を選ばせる案:** 長い推論に向かず、要求と能力が混ざります。
- **余りを cost や score に足す案:** 単位が違い、絶対 score も保てません。
- **ブラウザの Cookie で使用量を取る案:** アカウント全体を操作できる cookie を読むことになります。CLI の認証や API key で足ります。
